# 에스크로 헌법 (The Escrow Constitution)

> **헌법 제1조 (정의)**:
> 에스크로는 **"구매자가 돈을 맡기고(Deposit), 조건이 확인되면 판매자에게 풀리며(Release), 실패하면 구매자에게 돌아가는(Refund) 닫힌 보관함"**이다.

---

## 1. 절대 불변의 4대 헌법 조항 (Axioms)

1. **무자본 금지의 원칙 (No Empty Lock)**
   - 자금이 실제로 보관함에 입금(`Deposit`)되기 전에는 어떠한 이행이나 해제도 시작될 수 없다.
2. **단방향 종결의 원칙 (Terminal State Immutability)**
   - 이미 판매자에게 최종 지급(`RELEASED`)되었거나 구매자에게 반환(`REFUNDED`)된 자금은 영원히 다시 움직일 수 없다.
3. **자금 보존의 법칙 (Zero-Sum Conservation)**
   - `보관함 입금 총액(Deposit) = 판매자 누적 지급액(Released) + 구매자 반환액(Refunded)`.
   - 1원도 중간에서 증발하거나 허공에서 생성될 수 없다.
4. **승인자 배타성의 원칙 (Authority Separation)**
   - 지급(`Release`) 명령은 오직 **구매자(또는 합의된 서류 조건)**만이 내릴 수 있다.
   - 판매자는 절대 자의로 자금을 인출할 수 없다.

---

## 2. 단 2개의 거래 형태 (Constitutional Modes)

```
[공통 라이프사이클]:
  생성 (CREATED) 
     │
     ▼
  예치/잠금 (LOCKED)
     │
     ├─────────── [조건 만족] ───────────► 판매자 지급 (RELEASED)
     │
     └─────────── [조건 실패] ───────────► 구매자 반환 (REFUNDED)
```

### ① 개인 거래 (Simple P2P) : 단발 지급형
- **행위자**: 구매자 1명, 판매자 1명
- **해제 조건**: 구매자의 단순 승인 ("물건 수령 완료")
- **정산**: 전액(100%) 1회 일시불 지급
- **흐름**: `LOCKED` ➔ 구매자 승인 ➔ `RELEASED` (자금 100% 판매자에게 전송)

### ② 무역 거래 (Trade B2B) : 단계 분할형
- **행위자**: 수입자(구매자) 1명, 수출자(판매자) 1명
- **해제 조건**: 
  - 1차: 선적/서류(B/L) 제출 확인 ➔ 계약금 분할 지급 (예: 30%)
  - 2차: 물품 최종 통관/인도 확인 ➔ 잔금 지급 (예: 70%)
- **정산**: 100%를 단계별로 분할 지급하되, 분할 지급 총합은 최초 예치금과 정확히 일치함
- **흐름**: `LOCKED` ➔ 1차 서류 승인 ➔ 계약금 지급 ➔ 2차 검수 승인 ➔ `RELEASED` (잔금 지급 완료)

---

## 3. 헌법적 최소 데이터 스키마 (The Single Source of Truth)

이 헌법을 증명하기 위해 시스템 메모리 및 저장소에 존재해야 하는 데이터는 오직 아래 필드뿐이다:

```json
{
  "escrow_id": "거래 고유 식별자",
  "mode": "P2P | TRADE",
  "buyer": "구매자 식별자(지갑/ID)",
  "seller": "판매자 식별자(지갑/ID)",
  "total_amount": "최초 예치된 총 자금",
  "released_amount": "현재까지 판매자에게 지급 완료된 누적 자금",
  "refunded_amount": "현재까지 구매자에게 반환 완료된 누적 자금",
  "status": "CREATED | LOCKED | RELEASED | REFUNDED"
}
```

---

## 4. 금기 사항 (Anti-Patterns)
- 자금 입금 확인 없이 상태를 잠금(`LOCKED`)으로 변경하는 행위
- 종결(`RELEASED`, `REFUNDED`) 이후 잔액을 재조작하는 행위
- 구매자의 의사나 명시적 계약 조건 없이 판매자에게 임의 송금하는 행위
