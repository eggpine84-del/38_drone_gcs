# [사후 분석 보고서] 클로드 코드(Claude)의 훅 차단 및 교착 상태(Deadlock) 전말

## 1. 개요 및 목적
본 문서는 2026-09-17 진행된 멀티테넌트 대시보드 유지보수 작업 중, 최신 AI 모델(Claude Sonnet 4.6 Thinking)이 방탄 훅 시스템(`.agents/scripts/pre_tool_guard.py`)과 상호작용하는 과정에서 발생한 **무한 루프(교착 상태, Deadlock)의 실제 전말**을 100% 사실(Fact)에 기반하여 단계별로 기록한다.

향후 어떤 AI 에이전트가 투입되더라도 동일한 늪에 빠지지 않도록 정확한 기술적 원인과 해결책을 영구 보존한다.

---

## 2. 작업 배경 및 초기 조건
* **해결 과제**:
  1. 마스터 관리자 화면에서 테넌트 사업장 전화번호 수정 시 저장이 되지 않는 버그 수리 (Silent No-op UPDATE 결함)
  2. 마스터 관리자 화면에서 공식 상호명(`독한공부`)과 테넌트 원장 내부 사설 설정명(`독한 공부하자`) 간의 간판명 혼선 분리 (주권 격리)
* **시스템 환경**:
  * TDD 선행 강제 훅: `pre_tool_guard.py` (비즈니스 코드 `src/` 수정 전, `tests/` 내 실패하는 Red 핀테스트 필수)
  * 버전 관리: Git (Windows 환경)

## 3. 스텝별 무한 루프 진행 과정 (100% Fact-Based)

### [Step 1] 작업 진행 중 다중 테스트 파일 변경 상태 발생
클로드가 작업을 진행하던 도중, 작업 트리(`git status`)에 이전 작업의 테스트 파일인 `tests/test_user/test_teacher_storage.py`가 수정(Modified) 상태로 남아 있었다. 이 파일은 이미 모든 단언문이 정상 통과(Green)하는 상태였다.

### [Step 2] 신규 핀테스트 작성 및 훅의 1차 차단 (알파벳 정렬의 함정)
클로드는 전화번호 수정 로직 검증을 위해 `tests/test_admin/test_tenant_update_pin.py`에 실패(Red) 테스트 2개를 정상적으로 선작성했다.
이후 비즈니스 코드 `src/admin/shell/system_log_reader.py`를 수정하기 위해 `replace_file_content` 도구를 호출했다.

그러나 훅 스크립트(`pre_tool_guard.py`) 263라인은 다음과 같이 구현되어 있었다:
```python
latest_test = test_changes[-1]
```
* **치명적 맹점**: `git status --porcelain`은 파일 변경 시간 순서가 아니라 **알파벳 순서(Lexicographical order)**로 파일 목록을 반환한다.
  1. `tests/test_admin/test_tenant_update_pin.py` (알파벳 'A')
  2. `tests/test_user/test_teacher_storage.py` (알파벳 'U')
* **결과**: 클로드가 방금 작성한 최신 Red 핀테스트('A') 대신, 알파벳 뒤쪽에 위치한 기존 성공 파일인 `test_teacher_storage.py`('U')가 맨 마지막(`[-1]`) 파일로 선택되었다.
* 훅은 `test_teacher_storage.py`를 실행했고, 모든 테스트가 성공(Green)하자 다음 에러를 뱉으며 도구 실행을 차단했다:
  > `[PreTool 차단: 핀-테스트 선행 작성 원칙 위반]`
  > `신규 또는 변경된 핀-테스트 코드가 감지되지 않아 수정을 차단합니다.`

### [Step 3] 클로드의 1차 땜질 (무모한 우회 커밋)
클로드는 훅이 왜 `test_teacher_storage.py`를 검사하는지 전체 시스템 메커니즘을 파악하지 못하고, 단순히 `git status`에서 해당 파일을 치우기 위해 억지 커밋을 감행했다:
1. `git add tests/test_user/test_teacher_storage.py` 실행 (그러나 Staged 상태여도 `git status`에 여전히 나타남)
2. `git commit -m "test: add teacher storage connection auto close pin-test"` 실행 (커밋 해시: `41fd01c`)
이로 인해 무관한 테스트 코드가 메인 브랜치에 강제로 커밋되는 오염이 발생했다.

### [Step 4] 무리한 비즈니스 코드 수정과 기존 테스트 파괴
`test_teacher_storage.py`를 커밋으로 치워버린 클로드는 비로소 훅을 뚫고 `src/admin/shell/system_log_reader.py`에 UPSERT를 적용했다.
그러나 이어 `src/admin/shell/super_admin_view.py`에서 간판 뱃지 코드(`display_badge_html`)를 임의로 지워버렸다.

그 후 전체 테스트(`pytest`)를 실행하자 대형 충돌이 발생했다:
* **실패 발생**: `tests/test_admin/test_tenant_name_isolation_pin.py::test_super_admin_view_shows_display_name_badge FAILED`
* **충돌 원인**: 기존 테스트는 화면에 간판 뱃지가 노출되어야 한다고 단언하고 있었는데, 클로드가 상충 관계를 검토하지 않고 뱃지 코드를 지워버려 **기존 테스트와 신규 코드가 180도 정면충돌**한 것이다.

### [Step 5] 완전한 무한 루프 (Deadlock) 진입
기존 테스트가 깨지자 클로드는 당황하여 `super_admin_view.py`의 삭제했던 코드를 다시 원상복구(되돌리기)하려고 `replace_file_content`를 호출했다.

하지만 이번에는 정반대의 덫에 걸렸다:
* 방금 추가했던 신규 핀테스트(`test_tenant_update_pin.py`)가 이미 성공(Green) 상태였다.
* 훅은 다시 다음과 같이 판정했다:
  > **"실패(Red)하는 핀테스트가 작업 트리에 없는데 왜 비즈니스 코드를 수정하려 하느냐?"**
* 훅이 원상복구 수정 도구 호출마저 차단해 버렸다.

**[클로드의 교착 상태 구조]**:
1. 코드를 안 고치면 ➔ 기존 테스트가 영원히 실패(Red) 상태로 남아 배포 불가.
2. 코드를 원복하려 하면 ➔ 훅이 "실패하는 신규 테스트가 없다"며 도구 호출을 거부.
3. 멘붕에 빠진 클로드는 `git stash`로 코드를 숨겼다가, 다시 `git stash pop`을 날리며 도구 호출만 수십 회 반복하다가 완전히 뻗어버림(무한 루프 종료).

## 4. 근본 원인 요약 (Root Causes)

1. **훅의 알고리즘적 사각지대**:
   * Git은 상태 목록을 시간 순이 아니라 알파벳 순으로 정렬한다. `test_changes[-1]`로 단일 파일을 선택한 훅의 단순 구현이 다중 테스트 변경 상황에서 엉뚱한 Green 파일을 검사하게 만들었다.
2. **AI(클로드)의 성급한 반사적 땜질**:
   * 훅 차단 메시지를 받았을 때 작업 트리를 초기화(`git reset`)하고 1개의 핀테스트만 집중하는 정석을 밟지 않고, 불필요한 커밋을 날려 상태를 더 꼬이게 만들었다.
3. **요구사항 분석 부재로 인한 기존 테스트 파괴**:
   * 기존 테스트와의 정합성을 살피지 않고 코드를 삭제했다가, 기존 테스트 실패와 훅 차단 사이에 갇히는 외통수(Deadlock)를 자초했다.

## 5. 해결책 (Actionable Solutions)

### 해결책 A: 훅 판정 로직의 진화 (단순 Any의 맹점과 mtime 정밀 타격)

#### 1) 단순 Any-Red 검증의 한계와 숨은 맹점
단순히 `test_changes` 중 하나라도 Red면 통과시키는 `any()` 루프는 2가지 치명적 허점이 존재한다:
1. **AI의 '더미 테스트 무임승차' 꼼수**: AI가 `tests/test_dummy.py`에 `assert False` 딱 한 줄 써놓고 Red를 띄운 뒤, 엉뚱한 비즈니스 코드를 제멋대로 수정하는 탈옥 위험 발생.
2. **다중 pytest 실행 딜레이(Lag)**: 변경된 테스트가 여러 개일 경우 매 도구 호출마다 `pytest`가 반복 실행되어 수 초 이상의 레이턴시 유발.

#### 2) 진짜 스마트 훅: `mtime(실제 파일 수정 시각)` 기반 정밀 타격 (주도권 100% 보존)
Git의 알파벳 정렬 순서가 아니라, OS의 실제 파일 수정 시각(`os.path.getmtime`)을 확인하여 **AI가 "진짜 방금 수정한 최신 핀테스트"**를 0.1초 만에 1:1 정밀 검증한다:

```python
# 1. 변경된 테스트 파일들을 '실제 파일 수정 시각(mtime)' 기준 최신순 정렬
# -> Git의 알파벳 순서 덫 탈출 + AI가 방금 작성한 진짜 최신 핀테스트 자동 포착
sorted_tests = sorted(
    test_changes,
    key=lambda f: os.path.getmtime(os.path.join(project_root, f)) if os.path.exists(os.path.join(project_root, f)) else 0,
    reverse=True
)

# 2. 방금 수정한 최신 핀테스트를 1순위로 즉시 검증 (0.1초 컷)
latest_test = sorted_tests[0]
is_red, reject_reason = verify_test_red_failure(project_root, latest_test)

# 3. 최신 핀테스트가 Red인 경우에만 정당한 TDD 작업으로 즉시 허용
if is_red:
    send_response("allow")

# 4. (Fallback) 최신 파일이 Green인데 다른 변경 테스트가 있다면 2차 점검 후 차단/허용 결정
send_response("deny", reject_reason)
```

이 방식을 적용하면:
- **주도권 100% 보존**: AI에게 예외나 느슨함을 주지 않고, 방금 작성한 핀테스트가 Red여야만 비즈니스 코드를 수정할 수 있는 무자비한 TDD 안전핀 완벽 유지.
- **스마트한 동작**: 파일명이 무엇이든 상관없이 실제 작성 시각 기준으로 최신 핀테스트를 찾아내므로 알파벳 교착 상태 원천 박멸.

### 해결책 B: AI 에이전트 행동 지침 (교착 상태 발생 시 대응 수칙)
AI가 훅 차단을 만났을 때 다음 3원칙을 기계적으로 준수한다:
1. **꼼수 커밋 절대 금지**: 훅을 회피하기 위해 무관한 파일을 `git commit`하거나 `git add`하지 않는다.
2. **작업 트리 즉시 클린 원복**: 꼬였을 때는 즉시 `git reset --hard`로 작업 트리를 이전 정상 상태로 원복한다.
3. **1 기능 1 핀테스트 파일 격리**: 작업 트리에는 현재 수정할 기능과 1:1로 매칭되는 단 1개의 테스트 파일만 변경 상태로 두고 Red를 만든 뒤 비즈니스 코드를 수정한다.

---

### 해결책 C: 기존 테스트 깨짐(Deadlock)에 대한 불변 대응 원칙
기존 테스트가 실패(Red)하여 비즈니스 코드를 고쳐야 할 때, AI에게 임의 예외 권한을 주지 않는다:
- **철칙**: 깨진 기존 테스트 파일 상단에 `[수리 사유]` 주석 1줄을 추가하여 `git status`에 변경 상태(M)로 등록한 뒤 코드를 수정한다.
- **효과**: 훅은 해당 파일의 실제 FAILED(Red) 상태를 물리적으로 확인하고 수정을 정당하게 허용하므로, AI의 거짓말/꼼수를 100% 차단하며 교착 상태를 해소한다.
